# 기술 추적 (Phase 2) 설계

작성일: 2026-08-14

기술 설명을 **사전에 등록**해 두고, 관련 기업을 주기적으로 갱신하며 화면에서 펼쳐 보는 기능.
Phase 1(즉석 실행)이 스크립트로 검증된 것을 화면과 스케줄러에 올린다.

## 전제 — Phase 0·1에서 실측된 것

| 항목 | 실측 |
|---|---|
| 특허 검색 | KIPRIS `getWordSearch`, 서비스 경로 `Sevice`(오타 아님), `patent`·`utility` 필수 |
| 출원인 → 기업 | **법인번호 정확 조인**. 이름은 표기가 달라 매칭 불가 (특허 "주식회사 엘지화학" vs DART "(주)LG화학") |
| 출원인 벌크 | 385,256건 중 법인번호 보유 **99.4%** |
| 검색어 길이 | **4~30자**. 7자 2,440건 → 27자 318건 → 86자 8건 → 251자 20,029건 |
| 기술당 기업 | 상위 20 출원인 중 분석 가능 **7~13개** |
| KIPRIS 한도 | 무료 **월 1,000회**. 스캔 1회 ≈ 키워드 5개 = 5회 |
| DART 한도 | 일 20,000건(계정 합산) + **분당 1,000회**(초과 시 IP 1시간+ 차단) |

## 결정 사항

- **자동 갱신 월 1회, 기본 on**
- **기술 목록은 최상위 메뉴** (기업 목록과 나란히)
- **기존 분석을 재사용한다.** 기술 특화 재분석은 하지 않는다 (아래 "보류" 참조)

## 자동 갱신이 실제로 갱신하는 것

성격이 다른 셋이 섞여 있어 처음에 혼동했다. 정리하면 **Phase 2가 새로 만드는 자동화는 하나뿐**이다.

| | 무엇 | 주기 | 비용 | 현재 |
|---|---|---|---|---|
| **A** | 특허 재검색 → 새 기업 발견 | 월 1회 | KIPRIS 5회/기술 | **신규** |
| B | 신규 사업보고서 수집 | 24시간 | DART 호출 | **이미 있음** (`check_and_download_reports`) |
| C | 새 보고서 분석 | B에 종속 | 보고서당 $0.0135 | **이미 있음** (`scheduler_auto_analyze`) |

기술로 발견된 기업도 `Company`에 등록되므로 **B·C는 자동으로 따라온다.** A가 할 일은
"새 출원인이 나타났나" 확인과 기업 등록까지다.

### 왜 월 1회인가

특허는 **출원 후 18개월 뒤 공개**된다. 오늘 그 기술을 시작한 기업이 검색에 잡히려면
1년 반이 걸린다. 실제 검색 결과의 출원일도 2014~2025로 넓게 퍼져 있어 최근 것만
몰려 나오는 구조가 아니다. 주 1회는 과잉이다.

월 1회면 한도도 여유롭다.

| 등록 기술 수 | 월 호출 | 한도 대비 |
|---|---|---|
| 50개 | 250회 | 25% |
| 100개 | 500회 | 50% |

## 데이터 모델

```
Technology
  id
  name                 "전고체 배터리"
  description          기술 설명문 (사용자 입력)
  keywords             JSON — LLM이 뽑은 것. 사용자가 고칠 수 있어야 한다
  max_companies        이 기술의 온보딩 상한 (비용 통제)
  is_active            갱신 대상 여부
  last_scanned_at
  created_at, updated_at

TechCompany            기술 ↔ 기업 (스캔 결과)
  technology_id
  company_id           nullable — 아직 등록 안 된 기업은 비어 있다
  corp_code            nullable
  applicant_name       특허상 이름 (DART명과 다르다)
  jurir_no
  patent_count
  keyword_hits         JSON — 몇 개 키워드에서 나왔나
  status               tracked / available / excluded
  exclude_reason
  first_seen_at        ← 신규 진입 판별
  last_seen_at         ← 이번 스캔에 나왔나
```

**스캔 이력 테이블은 두지 않는다.** 호출량은 `ApiCall`에 있고, 신규 진입은
`first_seen_at`으로 알 수 있다. 이력 테이블은 지금 쓸 곳이 없다.

`Analysis`에 손대지 않는다 — 기존 분석을 그대로 읽는다.

## 화면

```
/technologies              기술 목록 — 기업 수, 최근 스캔, 신규 진입 배지
/technologies/:id          기술 상세 (펼쳐보기)
```

기술 상세에 담을 것:

- 기술 설명 + 키워드 (편집 시 다음 스캔에 반영)
- **관련 기업** — 상태별로 나눈다. 처방이 다르기 때문이다
  - `tracked` 분석 결과 요약 → 클릭 시 `/companies/:id/reports/:reportId`로
  - `available` 특허는 많은데 아직 안 보고 있음 → 등록 버튼
  - `excluded` 법인번호 없음 (대학·연구소·개인·외국)
- **변동** — 신규 진입 / 이탈 기업
- 각 기업의 `키워드 N개` 표시 — 넓은 키워드 하나에서만 나온 대기업과 여러 키워드에
  걸친 곳은 성격이 다른데 특허 건수만으로는 안 갈린다

**기존 화면과 붙는 지점**: 기업을 누르면 이미 만들어 둔 보고서 상세로 간다.
분석 화면을 다시 만들지 않는다.

## 스캔 흐름

```
활성 기술 (월 1회 또는 수동)
  ↓ keywords로 특허 재검색            patent_search.search
  ↓ 출원인 집계                        aggregate_applicants
  ↓ 법인번호 조인                      match_companies
  ↓ TechCompany 갱신 (last_seen_at, 신규는 first_seen_at)
  ↓ available 상위 max_companies 등록  tech_pipeline.register_company
  ↓ (이후는 기존 스케줄러가 보고서 수집·분석)
```

## 비용 통제 — 세 겹

| 겹 | 무엇 |
|---|---|
| KIPRIS | `api_usage.check()`가 호출 **전에** 잔여를 보고 막는다 |
| 기술별 | `Technology.max_companies` |
| 전역 | `scheduler_auto_analyze` (기존 토글, 현재 off) — 분석이 실제로 도는지를 여기서 잠근다 |

기술 스캔 자체는 무료 한도만 쓴다. 돈이 나가는 건 C(분석)뿐이고 기존 토글이 잠그고 있다.

## 설정

```
TECH_SCAN_INTERVAL_DAYS   신규, 기본 30
TECH_SCAN_ENABLED         신규, 기본 true (AppSetting 토글 — 화면에서 끌 수 있어야 한다)
```

`AppSetting`의 `TOGGLES`에 항목 하나 추가하면 API·화면이 따라온다.

## 오류 처리

- KIPRIS 한도 초과 → `QuotaExceeded`. 스캔을 중단하고 다음 주기에 재시도.
  **부분 스캔 결과를 저장하지 않는다** — 일부 키워드만 반영되면 "이탈 기업" 판정이 틀어진다
- 검색 실패(키워드 1개) → 그 키워드만 건너뛰고 나머지로 진행. 로그에 남긴다
- DART 차단 → 기업 등록만 실패한다. `TechCompany`는 `available`로 남으므로 다음에 재시도

## 보류 — 기술 특화 재분석

**이번에는 하지 않는다.** 기존 3종 분석(종속회사·R&D·국가전략기술)을 그대로 보여준다.

### 무엇을 보류하는가

"이 **기술 관점**에서 이 기업이 무엇을 하고 있나"를 따로 뽑는 분석. 예를 들어
전고체 배터리 기술로 등록했다면, LG에너지솔루션의 사업보고서에서 전고체 관련
서술만 추려 정리하는 것.

### 왜 보류하는가

**비용이 기술 × 기업으로 곱해진다.** 보고서 1건당 $0.0135인데, 기술 10개 × 기업 10개면
스캔마다 $1.35다. 기존 3종 분석은 기업당 1회로 끝나지만 기술 특화 분석은 기술마다 새로
돌아야 한다.

그리고 기존 R&D·국가전략기술 분석이 이미 상당 부분을 담고 있다. 부족한지 먼저 봐야 한다.

### 나중에 판단할 기준

다음이 확인되면 붙일 가치가 있다.

1. **기존 분석으로 부족한가** — 기술 상세 화면에서 기존 R&D 분석을 읽었을 때
   "이 기술에 대해 이 기업이 뭘 하는지" 답이 나오는가. 실제 사용해 보고 판단한다
2. **원문에 근거가 있는가** — 국가전략기술 분석에서 배운 것: 사업보고서에 없는 것은
   길이를 늘려도 환각만 는다. 특정 기술에 대한 서술이 원문에 실제로 있는지 먼저 재야 한다
   (`section_extract`한 본문에서 기술 키워드 등장 횟수를 세면 된다)
3. **비용이 감당되는가** — 기술 수 × 기업 수 × $0.0135

### 붙인다면 어떻게

- `Analysis`에 새 유형을 추가하지 않는다. 축이 다르다
  (기존은 `company × report × type`, 기술 분석은 `technology × report`)
- 별도 `TechAnalysis` 테이블 + `BatchJob`에 job 종류 구분자 추가
- `batch_poller._distribute`가 결과 key를 `report_id`로 보고 `Analysis`에 꽂는 부분이
  유일한 결합 지점이다. 여기만 갈래로 나누면 된다
- `gemini_batch.py`는 `Analysis`를 전혀 참조하지 않으므로 그대로 재사용된다

## 구현되지 않은 선행 조건

**DART 기업 색인이 978/3,983에서 멈춰 있다.** 색인이 없으면 출원인의 법인번호로
`corp_code`를 역인출할 수 없어 `available` 판정이 안 된다.

실제로 방금 실행에서 삼성SDI(32건)·삼성전자(25건)·현대자동차(22건)·기아(15건)가
"DART 색인에 없음"으로 빠졌다. 색인만 채우면 전부 `available`로 올라온다.

DART IP 차단이 풀린 뒤 채워야 한다.

```bash
cd backend && DATA_DIR=../data python -m scripts.build_dart_index
```
